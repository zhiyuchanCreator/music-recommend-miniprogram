# Shfl Case Study：AI 音乐专辑发现小程序

> 项目时间：2026-07-07 → 2026-09-10（约 2 个月）
> 类型：个人独立项目（产品 / 数据 / 前后端 / AI 全链路）
> 代码：github.com/zhiyuchanCreator/music-recommend-miniprogram

---

## 一、为什么做？

### 真实问题

听歌的人都有这个体验：**歌单越刷越同质化**。算法推荐基于你听过的歌做相似扩展，结果是把你的口味越缩越窄。而想主动破圈的人面对的是另一个困境——乐评网站（RYM / Pitchfork）上高分专辑成千上万张，不知道从哪张开始。

### 目标用户

- 想拓展听歌范围的音乐爱好者
- 实体唱片 / 黑胶消费者（我的唱片店兼职经历让我直接观察过这个群体的选购决策）
- 用自然语言描述心情、而不是记得具体歌名的人

### 为什么是「专辑」而不是「歌」

专辑是音乐文化里最小的完整单元——有封面、有曲目顺序、有时代背景。以专辑为单位的发现，天然逼着推荐系统回答一个更有意思的问题：**如果你喜欢 X，下一张该听什么？为什么？**

---

## 二、我做了什么？

独立完成全部环节：产品定义、原型设计、数据采集与清洗、推荐算法、云开发后端、小程序前端。

### 产品层

- 6 个页面（首页 / 搜索 / 搜索结果 / 详情 / 我的 / AI 探索）+ 全局错误兜底页
- 核心流程：随机探索 / 分类筛选 / 自然语言提问 → 专辑详情 → 跨平台跳转试听 → 收藏反馈

### 数据层

- 设计 Album Schema v1（15+ 字段），100 张真实专辑，封面与曲目 100% 补齐
- 数据来源：RYM 42 张 / Pitchfork 28 张 / Metacritic 30 张，覆盖 69 个独立流派，年份跨度 1959-2016
- 可复跑的数据管线：种子 → 清洗 → 补封面/曲目 → 同步三处数据文件

### 算法层（项目核心差异化）

1. **Embedding 相似检索**：自研 `genre-feature-v1` 特征模型，76 维（流派加权 + 情绪标签 + 年代桶），L2 归一化后余弦相似度即点积
2. **用户 Memory**：云端 `recordInteraction` 记录行为（view/favorite/unfavorite/skip，含去重与负反馈），`getUserTaste` 按动作权重 × 时间衰减聚合品味画像；端侧 `taste.js` 用本地收藏/历史计算品味向量，离线也能个性化
3. **推荐解释**：每条相似推荐附理由（共享流派 / 同年代）；首页「为你推荐」排除已收藏已浏览、每张附「因为你常听 jazz」式解释
4. **RAG Agent**：自然语言提问 → GLM 意图解析（结构化 JSON）→ 专辑检索召回 → LLM 生成口语化推荐

### 工程层

- 微信云开发：9 个云函数（5 个数据管理 + 4 个 AI/Memory）
- 前端 6157 行（pages/components/utils），全链路异常兜底（云 → 缓存 → 内置数据 → 错误页）

### 关键技术选择及理由

| 选择 | 理由 | 放弃的方案 |
|---|---|---|
| 自研特征 Embedding（76 维） | 零外部依赖、可解释、可复算；百级数据量下效果已验证 | 直接调 LLM API 生成文本 Embedding（有成本、不可解释、维度不可控） |
| 云数据库内全量余弦 | 100 张专辑毫秒级算完，避免过度工程 | 外部向量库（Milvus/Pinecone，数据量撑不起） |
| Memory 双层（云 + 端） | 云端支撑跨端与 RAG，端侧保证离线可用 | 只做云端（离线体验差）或只做本地（无法跨端） |
| glm-4-flash（免费模型） | 零成本验证 RAG 全流程 | 付费大模型（验证阶段没必要） |

## 三、难在哪里？

### 难点 1：没有外部 API 预算，怎么做「真」Embedding

**失败尝试：** 最初打算直接调 Embedding API，但发现专辑的文本信息太薄（一句话简介），且 API 有成本、黑盒不可解释——「为什么这两张相似」答不出来。

**解决过程：** 换思路——音乐发现需要的不是语义相似，而是**乐理特征相似**。流派是现成的结构化信号，我把它做成特征空间：主流派 1.0 / 次流派 0.7 / 情绪标签 0.5 / 年代桶 0.6，76 维 L2 归一化。词表固化在 `embedding-vocab.json` 保证重算一致。

**验证：** Kind of Blue → A Love Supreme (0.805)、OK Computer → In Rainbows (0.805)、Illmatic → Ready to Die (1.000)——全部符合乐评共识。这个「自研模型 + 可验证样例」比「调了个 API」有说服力得多。

### 难点 2：本地跑得通 ≠ 云上跑得通

**现象：** 100 张专辑（每张带 76 维向量）云函数导入，控制台测试永远在 `Duration: 3000ms` 处失败。

**排查：** 日志显示每次都死在同一个时间点——不是数据问题，是云函数默认 3 秒超时。批量写入 + 冷启动轻松超过它。

**解决：** `config.json` 声明 60 秒超时 + 写入批次并发 10→20。但又发现 `config.json` 的超时在开发者工具部署时**经常不生效**（两次实测确认），控制台手动配置才是权威来源；还顺手发现 config.json 里空的 `envVariables` 会在重新部署时清掉控制台设置的环境变量。

**教训沉淀：** 部署配置本身也是代码，且要验证「部署后的实际配置」而不是「仓库里写了什么」。

### 难点 3：RAG 的检索空间对不上

**问题：** 用户问题是自然语言（「适合深夜写代码的专辑」），专辑向量是特征空间——两者不在同一空间，没法直接余弦检索。

**取舍：** 放弃「一步到位」的向量问答，改为两段式：第一段 LLM 做意图解析（输出 genres/artists/mood 的 JSON），第二段用结构化条件检索专辑、再把候选喂给 LLM 生成推荐。检索候选不足时自动补高分专辑兜底，保证任何问题都有可用回答。

### 难点 4（事故复盘）：一次真实的隐私事故

上线过程中，一份含本人真实姓名和手机号的个人文档被提交进了公开仓库。

**处理：** `git filter-branch` 重写全部历史并 force push，逐 commit 验证敏感字符串零残留；同时把真实 AppID、云环境 ID 从代码中替换为占位符，本地通过 gitignored 的 `project.private.config.json` / `env.config.js` 覆盖，开发体验不受影响。

**沉淀的规则：** 个人材料永不进版本控制；真实凭证只存在于 gitignored 的本地覆盖文件；提交前问一句「这文件十年后公开会不会尴尬」。

## 五、我学到了什么？

1. **前面的结构决定后面的速度。** P0 把 genre 数组化、Schema 预留 embedding 字段时看似过度设计，P2 做向量检索时直接省掉一轮数据重构。做数据设计时问「三个月后的我要用它干什么」。

2. **可解释性是推荐的护城河。** 「相似度 0.805」不如「因为你常听 jazz」有说服力；自研特征模型的黑盒劣势反而逼出了更好的产品设计。

3. **本地跑通只是 50%。** 云函数超时、config 不生效、环境变量被覆盖——所有部署配置都要在真实环境验证一次。

4. **事故是最好的素材。** 隐私重写历史、超时排查这类「翻车记录」经过完整复盘后，比功能清单更能体现工程判断力，前提是你真的记录了过程。

5. **复用模板：** 数据管线脚本化（种子→清洗→同步→导入四步固定）、云函数超时配置检查清单、敏感信息 pre-commit 检查——这些已沉淀为这个仓库的可复用约定。
